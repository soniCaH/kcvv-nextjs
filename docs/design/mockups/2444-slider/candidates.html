Resolved — two arrow registers, chosen by the content

Round 1 verdict. The card slider's chrome is right as it ships. On the filter row the same arrow "is clashing with the filters themselves — it almost looks like one of the filters." The swipe-only candidate is out.

Why it clashes. The arrow and the chip are the same object: cream fill, 2px ink border, 4px offset paper shadow, sharp corners, mono glyph. Beside a 320px card that skin reads as chrome because the scale gap does the work. Beside a 32px chip, at 32px, it can only read as a peer. So the variable is not where the arrow sits — it is what it is made of. That is the axis round 1 never tested: it moved the arrow four ways and never redrew it.

The rule under test: the arrow wears paper only where the content is not itself paper. All four hybrids below keep the card slider exactly as it ships and differ only in the small arrow's skin. Each is still applied to all five archetypes, so a pick is a pick for the whole site.

One correction rides along in every hybrid: the card overhang moves −20px → −16px, so the arrow's outer edge lands on PageContainer's 16px gutter instead of 4px past it. Visually indistinguishable, and it removes the measured page overflow.

Resize the window — the chrome's whole behaviour turns on viewport width, and two of these surfaces never overflow at desktop at all. The badge top-right reports live overflow per surface and whether the chrome is even alive. Measured on production, 2026-08-11

  • At desktop the card slider never slides. Production ships 3 related items on 11 of 12 sampled articles. 3 × 320 + 2 × 32 = 1024 inside a 1040 track → overflowsBy: 0 at 1440, 1280 and 1080. No arrow and no fade render above ~1072px. #2443's 8-item cap wakes it up (2784px, 2.7 screens), which is why the count toggle exists.
  • The same is true of TeamSectionNav: it ships three items (Wedstrijden · Spelers · Staf), so its overflow-x-auto is inert at every width above a phone.
  • The slider's −20px overhang pushes the page. pageOverflow: 4px measured at 600px and on iPhone 13 — the overhang is 20px against PageContainer's 16px gutter. Once scrolled the left arrow sits at x = −4.
  • The slider's fade and its arrow occupy the same strip. The fade is 24px from the edge; the arrow spans −20 → +28. The condition that turns the fade on is the same one that renders a 48px opaque button over its middle.
  • The slider's arrow lands mid-card, over the title. my-auto centres it on a 416px track while the 16:9 photo is only the top ~180px — which is the geometry behind the cream-on-cream complaint that bumped the overhang from −8 to −20. The fix moved a button horizontally whose problem was vertical.
  • FilterTabs's padding absorbs the first 40px of scroll. pl-0 → pl-10 mounts with the left arrow, so scrolling 40px moves the chips exactly 0px: measured on /nieuws at 1440, 900, 620 and 390, the first chip stays at the same viewport x while scrollLeft goes 0 → 40. Scroll back and it jumps. This is the same jank that got the flex-sibling fix rejected in #2429 — already shipped, by a different mechanism.

Two inherited claims that did not survive the check

  • #2448 does not affect HorizontalSlider. It never imports useScrollHint — it carries its own checkScroll, differing four ways: no ResizeObserver at all (the hook has one), no DEAD_ZONE (the hook uses 10px), an extra children-change effect (the hook has none), and clientWidth * 0.8 per click against the hook's fixed 200px. Two scroll-position detectors exist; the shared machinery is only the button.
  • #2447's mechanism is FilterTabs's, not the slider's. The "padding on a scroll track does not reserve a gutter" diagnosis is FilterTabs lines 104/110. The slider pads nothing — it overhangs. The overlap is real but arrives by a different route: 28px of the leftmost card sits under the button.
  • Two of the slider's five props are dead in production. title is never passed (the row renders its own EditorialHeading), so its internal <h3 class="mb-3 text-lg font-bold"> — raw Tailwind, off the type ramp — never renders. theme="dark" has no consumer. Only trackClassName is used, and only to override the default gap-3, so that never ships either.
  • Unrelated, but visible in the chip row above: A-Ploeg and A-ploeg are both live Sanity categories and render as two separate chips on /nieuws.
