what the ticket assumed what production says
"unknown ids return a generic grey shield" True, and the 302 Location names it: a real crest redirects to /<clubId>/logos/xl.png, a placeholder to /0/logos/xl.png. That is a cheaper tell than hashing bytes — but it still costs one round trip per club.
one failure mode Two. KV Bonheiden (447) returns a real per-club URL, HTTP 200, ?v=1, 180×180 RGBA — and every pixel is fully transparent. Neither the redirect target nor the version param sees it. Only reading pixels does.
?v=null might be the signal It is not. Two of the four shields are ?v=null; SK Laar (18444) and FC Inkad Diegem (60820) are ?v=1 and still resolve to /0/. Half the cases, no better.
"<Crest>'s disc can never fire on the PSD path" Sharper than that: it never fires at all. 348 logo values across the three fixture-bearing routes, zero null, zero border-current in the shipped HTML. The disc is dead code on every public route — so "promote the disc to card scale" means promoting something that has never rendered.
the crest is untested above 64px /share's CrestTile draws it at 150, 180, 236 and 300px inside a paper chip with a 5px ink border — a bigger crest than this card will ever show, already shipping to staff.
"the opponent card" (unscoped) Exactly one surface: <RelatedRow> on /wedstrijd/[matchId], per #2443's table. One card, one route. And the union that feeds it (RelatedContentItem, 6 members) has no club member yet — #2443's build adds it.
